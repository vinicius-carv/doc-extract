# doc-extract — Design

Date: 2026-11-16
Status: approved 2026-11-16

## 1. Intent

`doc-extract` is the flagship public repo of a full-stack developer (Java/Spring Boot, React, LLM document extraction) who wants to read as a strong mid-level hire for international remote roles and Brazilian companies. It turns a PDF contract into structured JSON in which **every field carries evidence** (page + exact quoted span), and it **measures itself**: a fidelity report scores extraction against ground truth.

It mirrors the author's real work (legal-document indexing migration, healthcare contract extraction with evidence per data point) using **only public or synthetic data**. Nothing from client work: no documents, schemas, field names, prompts or code.

What makes it special compared to "LLM wrapper" demos:
- evidence is verified by code, not trusted: a quote that is not on the cited page is flagged;
- quality is a number with a reproducible command behind it, comparable across runs (prompt version, model);
- the reviewer can click any field and see the quote highlighted on the rendered PDF.

## 2. Goals, non-goals, anti-goals

**Goals (v1)**
1. PDF → per-page text (text layer, OCR fallback) → Claude extraction → evidence verification → stored result.
2. Fidelity scoring against ground truth, per field / category / document / run, stored and comparable.
3. React UI: gallery, document view with PDF highlight, fidelity report, gated upload.
4. Production-grade engineering signals: modular code, Testcontainers, CI on GitHub Actions without API keys, Dockerfile, env-based config.
5. English-first README with a pt-BR line, real fidelity numbers table, architecture diagram, one-command local run.

**Non-goals (v1)**
- Deploying (Fly.io + Neon is the target, done in a later phase with a real environment).
- User accounts / auth / multi-tenancy.
- Custom field schemas defined from the UI.
- Portuguese documents.
- Async job queue infrastructure (Kafka, Rabbit, etc.).
- Native-PDF-to-Claude extraction mode (see §10, future).

**Anti-goals (failure even if it "works")**
- Any client-derived artifact in the repo or its history.
- Fidelity numbers that cannot be reproduced from the repo (`eval` command + committed corpus manifest).
- A demo that runs up an unbounded API bill or can be trivially abused once deployed.
- A tangled codebase: the scoring and evidence logic must be testable without Spring or the network.
- Hidden hallucinations: a field shown as "found" whose evidence is not actually in the document.

## 3. Constraints

- Stack: Java 21, Spring Boot 4.x, Maven multi-module, Postgres, React + TypeScript + Vite.
- LLM: **local-first.** Default provider is Ollama on the dev machine (RTX 5060 8 GB VRAM, 32 GB RAM, Ollama 0.40.x), default model `qwen3.5:9b`. Claude API via the official Anthropic Java SDK (`com.anthropic:anthropic-java`, 3.x) is a supported second provider, selected by config. No Claude key is used during v1 development.
- Data: CUAD v1 (CC BY 4.0, Atticus Project; attribution in README and `corpus/LICENSE-CUAD`) + synthetic documents generated by the repo.
- CI must never need `ANTHROPIC_API_KEY`.
- Windows dev machine; repo lives at a short path (`C:\Users\vinic\Documents\projects\doc-extract`).
- Public repo on GitHub under `vinicius-carv`; not created or pushed without explicit user approval.

## 4. Approaches considered

1. **Modular monolith, Anthropic SDK direct — CHOSEN.** One Spring Boot app, Maven modules `core` / `app` / `eval` / `web`. One stack, clear module boundaries, scoring testable as plain Java, one container to deploy later. Provider swap is a small interface of our own.
2. **Same monolith, Spring AI for the LLM layer.** Recognizable keyword and free provider swap, but trails new Claude features and obstructs fine control of the output schema, retries and token use, which is the hardest part here.
3. **Java API + Python extraction worker.** Better PDF/OCR tooling (PyMuPDF, OCRmyPDF) but two languages, two CI pipelines, two containers, and it dilutes the Java signal the repo exists to send.

User picked 1.

## 5. Decisions made with the user

| Topic | Decision |
|---|---|
| Document domain | CUAD as main corpus + small synthetic set of degraded scans for the OCR path |
| Demo shape | Public gallery of pre-run documents + live upload gated by per-IP rate limit, page cap and daily budget kill-switch |
| Hosting | Fly.io + Neon Postgres, **later phase**; v1 is deploy-ready only |
| Evidence UI | Highlight on the rendered PDF (pdf.js text layer) in v1 |
| Architecture | Approach 1 above |
| LLM provider | Local Ollama by default (`qwen3.5:9b`), Claude as optional provider; own `LlmExtractor` interface, no Spring AI (user did not pick Spring AI; our call, open to change) |
| Model choice | Picked by measurement: v1 includes a local-model bake-off on the corpus |

### 5.1 Feasibility spike (2026-11-16, throwaway)

`qwen3.5:9b` via Ollama `/api/chat` with `format` = JSON schema, `think: false`, `temperature: 0`, `num_ctx: 16384`, on a one-page synthetic services agreement with 11 fields:
- schema-valid JSON 4/4 runs, identical output across runs;
- quotes verbatim 11/11 every run (whitespace-normalized substring check);
- values semantically correct 11/11, including a correct `null` for an absent expiration date; formats vary (`250,000 USD` vs `US$250,000`, parties as one comma string), so normalization and a list type for parties are required;
- latency ~24–30 s per call after warm-up (first call 138 s incl. model load), dominated by ~620 output tokens; a 4.4k-token input took the same time as a 0.6k one;
- at 16k context the model runs 84% GPU / 16% CPU.

Implications: windows of ~6 pages (~5k tokens) are cheap on input; cost is output, so keep quotes short and fields per call bounded. A full corpus eval (~40 docs) is on the order of 1–2 h locally: acceptable for a nightly/manual run, not for CI (CI uses recordings).

## 6. System design

### 6.1 Modules

```
doc-extract/
  core/    plain Java 21, no Spring. PDF text, OCR, extraction contract, evidence check, normalization, scoring.
  app/     Spring Boot 4 web app. REST API, persistence (JPA + Flyway), worker, guardrails, serves built web assets.
  eval/    CLI (Spring Boot non-web or picocli on core+app persistence). Runs corpus, writes a fidelity run.
  web/     React + TS + Vite. Built by Maven (frontend-maven-plugin) into app's static resources.
  corpus/  manifest, CUAD subset files, synthetic generator output, ground truth JSON.
  tools/   synthetic generator (Java, in core or its own module — builder's call).
```

### 6.2 Pipeline (core)

1. **Ingest:** PDFBox loads the file, enforces page cap. For each page: extract text layer with character positions. If a page's text layer is empty or below a threshold (builder's call, e.g. < 20 non-whitespace chars), render the page to an image and OCR it with Tesseract (Tess4J, `eng`), keeping word boxes.
2. **Page-tagged text:** build the prompt input as page-delimited text (`<page n="3">…</page>`). The same per-page text is stored, because evidence is verified and highlighted against it.
3. **Extract:** `LlmExtractor` interface (input: page-tagged window + category set; output: candidate fields + token/latency usage). The JSON schema is generated once from the category set and shared by both providers. Per field the model returns: `value` (string, list for `PARTY_LIST`, or null), `evidence` (list of `{page, quote}` verbatim spans), `confidence` (low/medium/high). `null` means "not present" and is a valid answer. Normalization to typed values (ISO dates, durations, money) is done **in code**, not by the model.
   - **Windowing:** the document is split into page windows (`DOC_EXTRACT_WINDOW_PAGES`, default 6 for Ollama, overlap 1 page; for Claude default = whole document). Each window is one call. Candidates are merged per category: drop `UNSUPPORTED` evidence, then prefer verified evidence, then higher confidence, then earliest page; `PARTY_LIST` merges as a set. A category is null only if every window returned null.
   - **`OllamaExtractor` (default):** Spring `RestClient` → `POST {OLLAMA_URL}/api/chat`, `stream: false`, `format` = schema, `think: false`, `options.temperature: 0`, `options.num_ctx` (default 16384), model from `DOC_EXTRACT_MODEL` (default `qwen3.5:9b`). Usage from `prompt_eval_count` / `eval_count` / durations. Read timeout generous (first call loads the model, ~2 min observed). Cost recorded as 0 USD.
   - **`ClaudeExtractor` (optional, `DOC_EXTRACT_PROVIDER=claude` + `ANTHROPIC_API_KEY`):** Anthropic Java SDK, structured outputs via `output_config.format` (typed `.outputConfig(Class)` or manual `JsonOutputFormat` schema). Default model `claude-opus-5-5`, effort set explicitly (`medium` default). Thinking stays adaptive (cannot be disabled on Opus 5.5). Server-side refusal fallback (`fallbacks: "default"` beta); `stop_reason` checked before reading content. Prompt caching on static system prompt + schema. Note: Claude citations are incompatible with structured outputs, so evidence comes from our schema + verification. Must compile and have unit tests with a mocked client; a live smoke test runs only when a key is present (skipped otherwise).
   - Prompt version is a named constant recorded on every run, together with provider, model and window settings.
4. **Verify evidence:** for each non-null field, search the quote in the cited page's text with whitespace/hyphenation/OCR-tolerant normalization. Outcomes: `VERIFIED` (exact after normalization), `FUZZY` (similarity ≥ threshold, e.g. 0.9), `WRONG_PAGE` (found on another page; page corrected, flagged), `UNSUPPORTED` (not found anywhere). Store the matched char range for highlighting.
5. **Persist** document, pages, extraction run, fields, evidence status.

### 6.2.1 Multi-value fields and evidence (builder-check call)

A field carries `value` (scalar, or list for `PARTY_LIST`) plus a list of `evidence` items, each `{page, quote}`; one item per supporting span (e.g. one per party), possibly on different pages. Evidence verification runs per item. `field_result` stores the field; an `evidence` child table stores the items with status and char range. `ground_truth` likewise has one row per gold span.

### 6.2.2 Gallery seeding (builder-check call)

On startup an idempotent seeder (keyed by document sha256) imports `corpus/` documents, ground truth and the recordings of the **featured run** (a run id pinned in `corpus/manifest.json`) into the DB. The gallery and per-document scores show the featured run's extraction. So a fresh `docker compose up` with no API key shows a fully populated gallery and report. The image ships `corpus/` (small: ~40 PDFs).

### 6.3 Fields (v1 category set)

8–12 CUAD categories that have a concrete value (not yes/no clause presence). Proposed:
Parties, Agreement Date, Effective Date, Expiration Date, Renewal Term, Notice Period To Terminate Renewal, Governing Law, Cap On Liability, Termination For Convenience (value = notice text), Minimum Commitment, License Grant (scope text), Document Name.
Final list is fixed when the corpus subset is chosen (§6.5): drop categories with too few gold labels in the subset. Each category has a type (`TEXT`, `DATE`, `DURATION`, `PARTY_LIST`, `JURISDICTION`, `MONEY`) that drives normalization and matching.

### 6.4 Fidelity scoring (core, pure functions)

**Split scoring (decided with the user):** the two corpora are scored differently, and the README reports them separately.

- **CUAD → clause-level (span) scoring.** CUAD gold labels are clause spans, not typed values, so on CUAD we score whether the right text was found: predicted evidence quotes vs gold spans by character overlap on the same page (overlap ≥ 50% of the shorter span = hit; constant, documented). Per category: precision = predicted quotes that hit some gold span / predicted quotes; recall = gold spans hit by some predicted quote / gold spans. Plus presence accuracy (field null vs gold empty). Typed `value` is shown but not scored on CUAD.
- **Synthetic → value-level scoring.** Ground truth is exact typed values, so the rules below apply in full, plus evidence location (quote on the page where the generator placed the value).

Value-level rules, per (document, category):
- **Outcome:** `CORRECT`, `PARTIAL`, `WRONG`, `MISSED` (gold has value, prediction null), `SPURIOUS` (gold empty, prediction non-null), `TRUE_EMPTY`.
- **Value matching by type:** dates compared after parsing to ISO; durations normalized to months/days; party lists matched as sets after name normalization (case, punctuation, corporate suffixes), partial when overlap < full; text fields by token-level F1 against the gold span (CORRECT ≥ 0.8, PARTIAL ≥ 0.4 — thresholds are constants, reported in README).
- **Evidence accuracy:** predicted quote overlaps a gold span (char overlap on the same page) → evidence hit.
- **Aggregates:** precision, recall, F1 per category and overall; evidence-verified rate; unsupported-field rate (hallucination proxy); cost (input/output tokens, USD from a price table in config); latency.
- A **run** = (corpus manifest hash, prompt version, provider, model, window settings, effort if Claude, timestamp). Runs are comparable side by side.
- **Local-model bake-off (v1):** run the corpus with `qwen3.5:9b` plus up to two challengers that fit 8 GB VRAM (candidates: `gemma4:e4b` for its longer context, a Ministral 3 8B build); the best by overall F1 (ties: verified-evidence rate, then latency) becomes the featured run. The comparison table goes in the README. Each challenger model is a ~3–6 GB download that needs the user's OK when pulled.

### 6.5 Corpus

- **CUAD subset:** ~25 contracts chosen by a committed script/manifest (deterministic: ids listed in `corpus/manifest.json`), favoring documents with labels across the chosen categories and ≤ ~40 pages. Ground truth derived from CUAD's span annotations. CUAD spans are char offsets into its `.txt` files, not PDF pages: a converter maps each gold span to (page, char range) by locating the span text in our extracted page text; spans that can't be mapped are reported and excluded, never silently dropped.
- **Synthetic set:** ~15 documents from a generator: templated contracts (e.g. provider/service agreements) with randomized but recorded values for the same categories → PDF → degraded image PDF (rotation, noise, blur, JPEG artifacts, at fixed seeds). Ground truth is exact by construction. Generator is deterministic from a seed and committed; generated PDFs are committed too so runs don't depend on regeneration.
- README states clearly which numbers come from CUAD and which from synthetic data.

### 6.6 Persistence (Postgres, Flyway)

Tables (indicative): `document` (id, source: CUAD|SYNTHETIC|UPLOAD, title, sha256, page_count, storage path, created_at), `page` (document_id, number, text, source: TEXT_LAYER|OCR, ocr_confidence), `extraction` (id, document_id, run_id, status, model, prompt_version, tokens, cost, latency, error), `field_result` (extraction_id, category, value, normalized, page, quote, confidence, evidence_status, match_start, match_end), `ground_truth` (document_id, category, value, page, start, end), `eval_run` (id, manifest_hash, model, prompt_version, effort, started/finished, aggregates JSONB), `field_score` (eval_run_id, document_id, category, outcome, evidence_hit), `job` (id, extraction_id, state, attempts, locked_until) for the worker, `usage_ledger` (day, spent_usd) for the budget.
PDF bytes stored on local filesystem volume (path in config); deploy phase may switch to object storage behind a `BlobStore` interface.

### 6.7 API (app)

- `GET /api/documents?source=` — gallery list with latest extraction summary.
- `GET /api/documents/{id}` — metadata, fields with evidence status and highlight ranges, per-field score if ground truth exists.
- `GET /api/documents/{id}/pdf` — PDF bytes.
- `POST /api/uploads` — multipart PDF; returns document id + job id (202).
- `GET /api/jobs/{id}` — state (QUEUED, RUNNING, DONE, FAILED) for polling.
- `GET /api/eval-runs`, `GET /api/eval-runs/{id}`, `GET /api/eval-runs/compare?a=&b=`.
- OpenAPI via springdoc; errors as RFC 9457 problem details.

### 6.8 Worker

In-process worker polling the `job` table with `SELECT … FOR UPDATE SKIP LOCKED`, bounded thread pool (config, default 2), retries with backoff on retryable SDK errors (429/5xx/connection), max attempts 3, stale-lock recovery via `locked_until`. Upload path and eval CLI share the same pipeline code.

### 6.9 Guardrails (built and tested in v1, active by config)

- Upload: PDF magic bytes + content type check, max size (e.g. 10 MB), max pages (e.g. 10), reject encrypted PDFs.
- Per-IP rate limit (e.g. 3 uploads/hour, Bucket4j in-memory; respects `X-Forwarded-For` only behind a configured trusted proxy).
- Daily budget kill-switch: estimated cost reserved before the call, actual cost recorded after; when the day's ledger reaches the limit, uploads return 503 with a friendly message and the gallery keeps working.
- Uploaded documents: not listed in the public gallery, visible only via their id; deleted after N days (scheduled cleanup, config).
- `UPLOADS_ENABLED` flag to turn uploads off entirely.

### 6.10 Web UI

- **Gallery:** cards for CUAD and synthetic docs (title, source badge, pages, F1 for that doc, evidence-verified %).
- **Document view:** two panes. Left: PDF rendered with react-pdf (pdf.js) including text layer. Right: field list (value, confidence, evidence status badge, score vs ground truth when available). Clicking a field scrolls to its page and highlights the quote on the text layer (match by the stored char range mapped onto text-layer spans; for OCR pages, highlight via OCR word boxes as overlay rectangles). Toggle to show gold spans.
- **Fidelity report:** run summary (P/R/F1, verified rate, unsupported rate, cost per doc, latency), per-category table, per-document drill-down, compare two runs.
- **Upload:** drag-and-drop, limits shown up front, progress via job polling, then redirect to document view.
- Simple, clean, responsive; no design system dependency beyond a small CSS approach (builder's call: plain CSS modules or Tailwind).

### 6.11 Testing and CI

- `core`: unit tests for normalization, matching, scoring, evidence verification (table-driven, many edge cases), PDF text extraction on fixture PDFs, OCR on one small fixture (tagged, may be skipped where Tesseract is missing locally; runs in CI).
- `app`: Spring Boot integration tests with **Testcontainers Postgres**; API tests (MockMvc or RestClient); worker tests; guardrail tests (rate limit, budget, page cap).
- **LLM in tests:** `RecordedExtractor` replays stored provider responses keyed by (document sha256, window index, prompt version, provider, model). Fixtures recorded by running `eval --record` locally against Ollama; committed under `corpus/recordings/`. CI never needs Ollama or an API key. CI runs the full eval on recordings and asserts fidelity is not below a committed baseline (regression gate).
- `web`: Vitest + React Testing Library for components; one Playwright smoke test against the built app with recordings (builder's call whether in v1 CI or local only).
- GitHub Actions: build + test on push/PR (Java 21, Node LTS, Tesseract installed via apt), Docker image build (no push). Badges in README.

### 6.12 Packaging and config

- Multi-stage Dockerfile: build web + jar, runtime on a JRE 21 base with `tesseract-ocr` + `tesseract-ocr-eng`.
- `docker-compose.yml` for local: app + Postgres. The app reaches the host's Ollama at `http://host.docker.internal:11434` (`OLLAMA_URL`); Ollama itself is not containerized (GPU passthrough on Windows Docker is out of scope). If no provider is reachable, the app runs in "replay only" mode: gallery and report work, uploads disabled with a clear message.
- All config via env vars: DB URL/credentials, provider, model, window pages, num_ctx, Ollama URL, Claude key/effort, budget, rate limits, upload limits, storage path, retention days.
- Daily budget kill-switch (§6.9) applies to paid providers; with Ollama it is inert (cost 0) but the per-IP rate limit and page cap still apply, and a concurrency limit of 1 in-flight Ollama call protects the GPU.

## 9. Risks

- **CUAD span-to-page mapping** may fail for some spans (PDF text vs CUAD txt differences). Mitigation: tolerant matching, report unmapped spans, pick subset documents that map cleanly.
- **Highlight precision on pdf.js text layer** (text-layer items don't align 1:1 with PDFBox text). Mitigation: match by normalized text search within the page's text-layer content, fall back to page-level highlight.
- **Local eval time** (~25–30 s per window): a full corpus run is 1–2 h. Mitigation: `eval --docs`/`--limit` for fast iteration on a subset; full runs only to record.
- **Small-model quality** on long, messy CUAD contracts may be much lower than on the spike's clean page. That is a finding to report, not hide; the Claude provider and bake-off exist to show the trade-off.
- **Tesseract quality** on heavily degraded scans: degrade levels are tuned so OCR is challenged but not hopeless; the report separates OCR-page accuracy.
